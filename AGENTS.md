# AGENTS.md

This file provides guidance to LLM agents (e.g. claude.ai/code) when working with code in this repository.

## Project shape

Cargo workspace (`Cargo.toml`) with three crates:

- `db` — Diesel + SQLite data layer. Defines models, schema, the `SwordDrillable` trait, and the production `SwordDrill` implementation. Owns the migrations and connection-pool plumbing.
- `web` — Actix Web server (binds `0.0.0.0:8080`). Renders Handlebars views and a JSON API.
- `cli` — Small `clap`-based binary that resolves a single Bible reference using the same `db` crate.

Bible text lives in a single SQLite database; full-text search is the SQLite **FTS5** extension. Migrations live in a **git submodule** at `db/migrations` (`https://github.com/DSpeckhals/bible.rs-migrations`). After cloning, run `git submodule update --init --recursive` or migrations will fail to apply.

## Build / lint / test

The CI workflow (`.github/workflows/ci.yml`) is the source of truth — mirror it locally:

```sh
cargo fmt -- --check
cargo clippy --all-targets --all-features --all
cargo build --all
cargo test --all
```

Run a single test by path, e.g. `cargo test -p db sword_drill::tests::all` or `cargo test -p web view::tests::reference`.

Run the server locally with `cargo run -p web` (set `DATABASE_URL`; defaults to `/tmp/biblers.db`). Run the CLI with `cargo run -p cli -- "John 3:16"` (CLI **requires** `DATABASE_URL`).

## SQLite

`libsqlite3-sys` is configured with the `bundled` feature, which compiles a vendored SQLite amalgamation (FTS5 enabled) into the binary at `cargo build` time. No system `libsqlite3` is required at build or runtime; no `clang`/`libclang`/`llvm` either. Builds need only a C compiler (`cc`), which is present in the `rust:trixie` Docker image and on GitHub-hosted runners.

## Working-directory assumptions

Several paths are **hardcoded relative to the workspace root** and the binaries assume they are launched from there:

- `db::run_migrations` opens `./db/migrations` (in `db/src/lib.rs`).
- `web/src/main.rs` registers Handlebars from `./web/templates/` and serves static from `./web/dist`.
- `web/src/error.rs` (`ERR_TPL`) loads `./web/templates/base.hbs` and `error.hbs` at first error.

If you add a new path, follow this convention or change all of them together. The Dockerfile reflects this layout (`WORKDIR /app` with `web/dist`, `web/templates`, `db/migrations` copied in).

## Controllers are generic over `SwordDrillable`

`db::SwordDrillable` is the data-access trait; `SwordDrill` is the real impl and `web::test::TestSwordDrill` is the in-memory mock used by handler tests. Every controller in `web/src/controllers/{api,view}.rs` is `pub async fn foo<SD: SwordDrillable>(...)`, and `main.rs` wires `::<SwordDrill>` while `web/src/test.rs` wires `::<TestSwordDrill>`. When adding a handler, keep this generic shape so tests don't need a real database.

## Diesel schema split

`db/src/schema/auto.rs` is **generated by `diesel print-schema`** (see `db/diesel.toml`) and excludes the FTS5 virtual tables. `db/src/schema/mod.rs` re-exports `auto` and adds a hand-written `verses_fts` `table!` plus `allow_tables_to_appear_in_same_query!(books, verses_fts)`. After regenerating `auto.rs`, do not lose the manual additions in `mod.rs`.

## URL routing order matters

In `web/src/main.rs` the `{book}` resource is registered **before** `{reference:.+\d}`. The reference path captures the rest of the URL (e.g. `Psalms/119/105`), and `view::reference` / `api::reference` convert `/` to `.` before parsing via `Reference::from_str`. Don't reorder these or both routes will collide.

Two more ordering constraints exist in the same chain:

- `/robots.txt` and `/sitemap.xml` resources must be registered **before** `{book}`, or the catch-all matches them as a book name.
- `/static/js/sw.js` resource (which sets `Service-Worker-Allowed: /`) must be registered **before** `actix_files::Files::new("/static", ...)`, or the static-file service matches first and the header is lost — breaking the SW registration in `web/dist/js/main.js`.

## Frontend assets

CSS is compiled from `web/styles/*.scss` to `web/dist/css/style.css` with `sassc` (the Dockerfile runs this; there is no Cargo build step for it). Static assets in `web/dist/` are served at `/static`.

## Deploy

Hosted on **Fly.io** as a single container with one persistent volume.

- App config: `fly.toml` (region `iad`, default 256MB shared VM, volume `biblers_data` mounted at `/opt/data`, scale-to-zero with auto-start).
- Database: `DATABASE_URL=/opt/data/bible.db` on the Fly volume. Migrations run at startup from `./db/migrations/` — the **submodule must be checked out** before any image build (`git submodule update --init --recursive` locally; `submodules: recursive` in CI).
- TLS / domains: Fly terminates TLS for `bible.rs` and `www.bible.rs`. The `www → apex` 301 is performed in-app via a `wrap_fn` middleware in `web/src/main.rs`. HTTP→HTTPS is handled by Fly's edge (`force_https = true`).
- Security headers (HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, CSP) are applied in-app via `DefaultHeaders`. The CSP includes `'unsafe-inline'` in `script-src` to allow the inline JSON-LD block in `base.hbs`.
- Tagged pushes (`refs/tags/*`) trigger `.github/workflows/deploy.yml`, which runs `flyctl deploy --remote-only`. The remote builder builds from the repo's `Dockerfile`. No GHCR; no SSH; no nginx; no certbot.
- Manual deploy: `flyctl deploy --remote-only -a biblers` from a working tree with the submodule materialized — flyctl tars the local tree, so an empty `db/migrations/` will produce a binary that crash-loops at startup when migrations try to load.
- Single-machine constraint: the volume pins the app to one machine in one region. Each deploy stops the machine, swaps the image, and restarts (a few seconds of downtime per deploy). For HA, see Fly's LiteFS or move SQLite off-box.
